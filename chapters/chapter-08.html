Learn how Linux organises every file in one tree: what each folder is for, why /bin is a shortcut to /usr/bin, and why some commands need root.

8.1.1

Root Directory Structure

📌
Study order

Read the chapters in this order: Chapter 1 → Chapter 2 → Chapter 8 (this chapter) → Chapter 3 and on. Chapter 3 (managing files) uses the folder names you learn here, such as /, /etc, /usr and /var. Next: <a href="chapter-03.html">Chapter 3 · Managing Files from the Command Line →</a>

What is a file system?

Think of a very big filing cabinet. It has drawers (folders), and each drawer can hold papers (files) or smaller folders. Linux keeps everything this way: your documents, the programs you run, your settings, even your hardware.

  • A folder is also called a directory. They mean the same thing.
  • The whole arrangement of folders and files is called the file-system hierarchy. "Hierarchy" just means "organised in levels".

One tree, one starting point

In Linux every file lives in one big tree. The tree is drawn upside down: the starting point is at the top, and the branches (folders) grow downward.

  • The starting point is called the root directory. It is written as a single slash: /.
  • The same / character is also used to separate folder names in an address (a path).
/etc/issue is the full address of the file called issue.

So /etc/issue means: start at /, open the folder etc, and find the file issue.

Windows vs Linux

No drive letters in Linux: everything hangs from one starting point called / (the root).
  • Windows has separate drives: C:\, D:\, E:\. Linux has one tree that starts at /.
  • If you add another disk or USB stick, Linux attaches it to a folder somewhere in the tree. This is called mounting.
⚠️
Easy to confuse: / vs /root vs /home/root

/ is the top of the whole tree.

/root is the home folder of the root user (the administrator).

/home/root does not exist as root's home. Normal users live in /home/name, but root is special and has its own /root.

8.1.3

Directory Organization: the /bin and /usr Story

Why do /bin and /usr/bin both exist? (the "merged" folders)

Look at the tree again. You see /bin, /sbin, /lib and /lib64 next to /usr. And inside /usr you also see bin, sbin, lib and lib64. That looks like duplicates, but it is not. Here is the simple answer:

✅
Short answer

/bin is only a shortcut (symbolic link). The real folder is /usr/bin. The same is true for the other three: /sbin → /usr/sbin, /lib → /usr/lib, /lib64 → /usr/lib64.

/bin is only a shortcut that points to /usr/bin. The same is true for /sbin, /lib and /lib64.
Shortcut (link)Points to (real folder)Contains
/bin/usr/binEveryday commands
/sbin/usr/sbinAdmin commands
/lib/usr/libShared libraries (code that programs share)
/lib64/usr/lib6464-bit shared libraries

What is a symbolic link?

A symbolic link (symlink) is like a shortcut on your desktop: it is a tiny file that just says "go over there". Opening the shortcut takes you to the real folder.

Prove it on your own machine

Terminal$ ls -ld /bin /sbin /lib /lib64 lrwxrwxrwx. 1 root root 7 Jan 1 10:00 /bin -> usr/bin lrwxrwxrwx. 1 root root 8 Jan 1 10:00 /sbin -> usr/sbin lrwxrwxrwx. 1 root root 7 Jan 1 10:00 /lib -> usr/lib lrwxrwxrwx. 1 root root 9 Jan 1 10:00 /lib64 -> usr/lib64 $ readlink -f /bin # where does the shortcut really go? /usr/bin $ ls -i /bin/ls /usr/bin/ls # same inode number = the very same file 1234567 /bin/ls 1234567 /usr/bin/ls
  • The first letter l means link. The -> arrow shows where it points.
  • The size (7, 8, 9) is just the length of the text usr/bin, usr/sbin, and so on.
  • Your numbers and dates will differ; the l and the arrows are what matter.

Why was it done?

  • Long ago, disks were small. The first disk held only the few tools needed to start the system (/bin, /sbin, /lib). A second disk held the rest (/usr).
  • Today disks are huge and the system starts in a different way, so keeping two separate sets is pointless. It even caused confusion about which copy was used.
  • Since RHEL 7, all real files live in /usr. The old names stay as shortcuts so old programs and scripts that say /bin/bash still work.

What this means for you

  • /bin/ls and /usr/bin/ls are the same file. which ls usually shows /usr/bin/ls.
  • Put your own programs in /usr/local/bin, not in /usr/bin. /usr/bin is managed by the package manager.
  • Never delete or replace the links. Many things would break.

💡
Memory trick

bin = "things I use." sbin = "things the system administrator uses."

⚠️
Common wrong idea

The folder name does not stop you from running a command. Permissions decide that.

  • Some programs in /usr/sbin work for normal users, for example ip a.
  • Some programs in /usr/bin need root for certain actions.
  • sbin is only a hint: "this is meant for admins".

How does the shell find a command? (PATH)

When you type ls, the shell looks through a list of folders called PATH, one by one, until it finds a program with that name.

Terminal$ echo $PATH # the list of folders the shell searches $ which fdisk # where is this command? /usr/sbin/fdisk $ type -a ls # every match
  • If a command says "not found" but exists, run it with its full path: /usr/sbin/fdisk -l.
  • /usr/local/bin is for your own programs. /usr/local/sbin is for your own admin programs.
📘
Newer change to know about

Newer Fedora versions have also merged /usr/sbin into /usr/bin. RHEL 10 still keeps both, so learn them as two separate folders.

Why do installers make /boot, /home and /var separate?

Each folder has a different job. If /var (logs) fills up and it shares the disk with /, the whole system can freeze. A separate partition keeps that damage small, and a separate /home keeps user files safe if you reinstall.

8.1.4

Why Can Root Run fdisk but I Cannot?

This is a very common question: "Why can root run fdisk, but I cannot?" The answer is in file permissions.

Step 1: hardware is shown as files

In Linux, a disk appears as a file inside /dev, for example /dev/sda. To read or change the partition table, fdisk must open that file.

Step 2: read the permissions

Terminal$ ls -l /dev/sda brw-rw----. 1 root disk 8, 0 Oct 11 10:02 /dev/sda
brw-rw----
Type: b = block device (a disk)
Owner (root): read + write
Group (disk): read + write
Everyone else: nothing
  • You are not root and (normally) not in the disk group, so you are in "everyone else": no access.
  • Root (user ID 0) is allowed to open everything, so root can use fdisk.
Terminal$ fdisk -l fdisk: cannot open /dev/sda: Permission denied $ sudo fdisk -l # works: lists the partitions # fdisk -l # works as root

Your disk may be named /dev/sda, /dev/vda or /dev/nvme0n1.

Why is it built this way?

  • Changing a partition table can wipe all data on a disk.
  • Blocking normal users from raw disks protects the system from mistakes and bad programs.
  • This idea is called least privilege: give only the power that is needed.

Good habits

  • sudo fdisk -l only looks. It changes nothing.
  • sudo fdisk /dev/sda opens a menu. Nothing is saved until you press w. Press q to quit without saving.
  • Do not add yourself to the disk group to avoid typing sudo. That gives your account raw access to the whole disk.
  • You can run lsblk without root. It lists your disks safely.
💡
Rule to remember

Command found but still Permission denied? That is a permissions problem, not a missing command.

Practice on Your VM

Practice$ pwd $ ls -la $ cd /var/log && pwd $ cd - && pwd # jump back to the previous folder $ cd ../.. && pwd $ cd ~ $ ls -ld /bin /sbin /lib /lib64 # four shortcuts into /usr $ readlink -f /bin # prints /usr/bin $ ls -l /dev/sda # who owns the disk file (name may differ) $ which fdisk ls $ echo $PATH $ fdisk -l # as a normal user: Permission denied $ sudo fdisk -l # works $ lsblk # works without root

8.3

Common Mistakes

  • Mixing up / (top of the tree), /root (the administrator's home) and /home/root (does not exist).
  • Thinking /usr/sbin commands are blocked for normal users. Permissions decide, not the folder.
  • Forgetting that /bin, /sbin, /lib and /lib64 are shortcuts into /usr.
  • Mixing up /tmp (cleaned after 10 days) with /var/tmp (30 days).
  • Thinking /run keeps its data after a reboot. It does not.
  • Putting your own programs in /usr/bin. Use /usr/local/bin.
📝
8.4

Summary

  • Linux keeps everything in one tree that starts at /.
  • Each folder has a job: /boot starts the system, /etc holds settings, /home holds user files, /var holds changing data like logs.
  • /bin, /sbin, /lib and /lib64 are shortcuts to the real folders inside /usr.
  • /usr/bin = everyday commands. /usr/sbin = admin commands.
  • /tmp is cleaned after 10 days. /var/tmp after 30 days. /run is cleared at reboot.
  • Hardware is shown as files in /dev, protected by permissions.
